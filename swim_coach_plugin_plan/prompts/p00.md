# Prompt de implementação — P00 Fundação e spikes de risco

Você está implementando a fase **P00** do projeto Swim Coach. Trabalhe diretamente no repositório atual e entregue código executável, testes e documentação. Não apenas descreva uma solução.

## Contexto obrigatório

Leia nesta ordem:

1. `AGENTS.md`
2. `MASTER_PLAN.md`
3. `IMPLEMENTATION_STATUS.md`
4. `phases/p00-foundation-and-spikes.md`
5. `docs/20-context-map.md`
6. docs/01, docs/08, docs/13, docs/15, docs/16, ADR-0001/0002/0006/0007
7. contratos citados pela fase
8. código/testes/migrations existentes

## Objetivo desta sessão

Criar um repositório executável e provar, antes de construir o domínio, que o caminho Plugin/MCP, OAuth e Garmin é viável no ambiente real do usuário.

## Restrições

- implemente somente P00; não antecipe fases futuras;
- preserve todos os invariantes de `AGENTS.md`;
- não invente integração como concluída;
- não use mock como evidência quando o gate exige sistema real;
- nunca exponha ou commite credenciais, tokens, FIT real ou dados pessoais;
- se um fato de plataforma puder ter mudado, valide em documentação oficial;
- prefira a menor alteração coerente;
- qualquer divergência arquitetural exige ADR ou registro explícito;
- não marque a fase `DONE` se o gate não foi demonstrado.

## Processo obrigatório

1. Inspecione estado, branch, mudanças locais, estrutura e comandos existentes.
2. Compare o código com as tasks da fase e escreva um plano curto por task ID.
3. Marque a fase `IN_PROGRESS` nos arquivos de status.
4. Implemente em fatias testáveis.
5. Execute lint, typecheck, unit, integration/contract/E2E aplicáveis.
6. Corrija regressões; não desabilite testes para obter verde.
7. Demonstre o gate com evidência sanitizada.
8. Atualize contratos, docs, status e changelog.
9. Produza o handoff definido em `docs/21-llm-handoff-protocol.md`.

## Critério de aceite da sessão

Plugin/MCP inofensivo funciona em uma superfície real; OAuth possui caminho viável; Garmin read é viável; repo sobe do zero; nenhum segredo vazou.

## Formato da resposta final

- resumo do que foi entregue por task ID;
- lista de arquivos e migrations relevantes;
- comandos/testes com resultado;
- evidências manuais/reais;
- riscos/limitações honestos;
- status final (`DONE`, `BLOCKED` ou `IN_PROGRESS`);
- próximo passo exato.

Não peça confirmação para começar. Quando uma dependência externa bloquear parte da fase, conclua tudo que for independente e registre o bloqueio com reprodução.
